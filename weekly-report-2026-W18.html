AI 测试平台 · 用例生成流程说明

模块测试用例生成 + 质量契约生成  |  仓库SuperAI / ai-test-platform  |  周次2026 W18 周会（2026-04-30）

适用范围：用户上传需求文档 → AI 生成测试用例 / 质量契约草稿， 结果可存入用例库或契约库后续使用。

一、当前生成流程

基于多步 Agent Pipeline（本周新增），前端 SSE 实时推流。 共分三个大步骤，最终通过流式输出将用例逐条送回前端。

①
前端输入组装 前端
用户在 TestCaseGenerationPage 填写：需求文档（可多份）、关注点文本 focusText、 测试类型 selectedTypes、深度 depth、LLM 通道选择。 代码变更文件通过 CodeChangePanel 接入 VCS（Git/Perforce）， 构成 GeneratePayload 发往后端。
②
Pipeline · Step 1 — 代码预分析 本周新增
从代码变更文件中选取最相关的 前 12 个文件（按关键词评分排序）， 按 并发 workers=3 批量调用 LLM 逐文件分析：
⚡ 并发区（每批次独立 LLM 调用，concurrency=3）
并
批次文件分析 新
小文件合批（≤18,000 字符/批，≤5 文件/批），大文件单独调用。 每文件输出：文件职责、需求相关性、关键接口（≤8）、入参校验与异常分支、边界条件、风险点（1-3）。 单文件截断阈值：30,000 字符。单文件失败降级为 stub（"信息不足：xxx"），不阻断整体。 超时：240s/次（PIPELINE_SINGLE_CALL_TIMEOUT_MS）。
③
Pipeline · Step 2 — 需求分析 本周新增 可接 RAG
汇总 Step 1 的代码分析结论 + 需求文档（截断阈值 60,000 字符）+ 知识库检索（RAG context）， 由 LLM 生成结构化需求分析报告：需求分解、缺失信息标注、测试风险识别。 若 Step 1 耗时超过 STEP_2_SKIP_AFTER_MS（默认 5 min）则跳过本步骤， 保证整体不超时。
④
Pipeline · Step 3 — 用例生成（流式） SSE 实时推流
接收 Step 2 预消化的需求分析作为输入，调用 server/prompt.js 构建最终 Prompt， 通过 OpenAI-compatible 接口流式输出用例。 前端通过 streamGenerateTestCases 逐 delta 接收，支持 AbortController 随时取消。 支持推理模型（DeepSeek-Reasoner / V4-Pro）的 thinking 过程透传展示。
⑤
结果解析 & 入库 前端
流结束后，解析得到 TestCase[]，展示在前端卡片列表。 用户可批量导入用例库（ImportToLibraryModal）或逐条编辑后保存。 生成会话状态通过 generationSessionCache 缓存，支持刷新后复原。

二、质量契约生成流程

质量契约是对功能模块「输入 → 行为 → 预期」的结构化描述，本周完成后端持久化与契约库页面。

①
输入 — 项目/模块 + 需求文档 + 代码上下文
契约必须绑定用例库中已有的 projectId + moduleId（后端 validateProjectModule 校验）。 支持上传需求文档并可附加关联代码文件（contractCodeContextForReview.ts）作为生成依据。
②
LLM 流式生成契约草稿 本周完善 SSE 流式
调用 openai-contracts.js 或 gemini-contracts.js 生成契约草稿， 通过 contractStreamParse.ts（本周新增）实时解析流式 JSON， 前端边流边渲染契约卡片（given / when / then_must 三栏结构）。 contractDraftStore.ts 管理草稿状态与 IndexedDB 持久化。
③
契约草稿编辑 & 归档 本周新增契约库页面
生成后在 QualityContractsPage 展示、编辑； 确认后通过 POST /api/quality-contracts 提交后端（qualityContracts.js） 存入 data/quality-contracts.json（原子写：先写 .tmp 再 rename）。 ContractLibraryPage（本周新增）提供跨会话的历史契约浏览与管理。

三、质量契约内容结构（参考约束）

每条契约的数据结构约束与验收标准。

字段 含义 约束 降级/验收
projectId
moduleId		 归属项目与模块（与用例库对齐） 必须在 case-library.json 中已存在；后端硬校验，不存在直接报错 报错："项目不存在" / "模块不存在或不属于该项目"
given 前置条件描述 LLM 生成，非空字符串 流式解析失败时 stub 占位
when 触发动作描述 LLM 生成，非空字符串 同上
then_must 必须满足的预期结果 LLM 生成，数组（≥1 条）；格式校验由 normalize-contracts.js 处理 normalize 兜底：将字符串 / 非标格式统一转为数组

四、本周调整与优化 （来源：commit cbb6558，2026-04-28）

① 新增多步 Agent 流水线 pipeline.jsserver/pipeline.js · 新文件 399 行

改了什么 将原来「单次 LLM 调用生成用例」拆分为三步 Pipeline： 代码预分析（每文件独立调用）→ 需求分析（结构化分解）→ 用例生成（流式输出）。 每步骤通过 onProgress 回调实时向前端推送 SSE 进度事件。
为什么改 原单次调用在代码量大、需求复杂时，LLM 上下文过长、输出质量不稳定； 拆步骤后每步输入精确，中间步骤失败可降级为 stub 继续走完，不让整体崩溃。
改完效果 用例生成时前端可看到「正在分析 X/Y 文件」进度提示； 代码相关性低的文件自动过滤（最多 12 个最相关文件），减少无效 token 消耗。

② 质量契约体系完善qualityContracts.js + ContractLibraryPage.tsx + contractStreamParse.ts · 共新增 ~670 行

改了什么 新增后端持久化模块 qualityContracts.js（JSON 文件原子写入）； 新增前端契约库页面 ContractLibraryPage（历史契约浏览/管理）； 新增流式解析器 contractStreamParse.ts（边流边渲染契约卡片）。
为什么改 之前契约只在当前会话内存在，刷新即丢失； 团队需要跨会话复用契约作为测试评审基准。
改完效果 契约草稿可持久化存储并在契约库中统一管理； 流式渲染让用户在生成过程中即可逐条预览，不需等待全部生成完毕。

③ 知识库（RAG）模块简化重构knowledgeStore.ts · 大幅精简

改了什么 knowledgeStore.ts 精简重构，去除冗余逻辑； 服务端 knowledge.js（277 行，新增）统一管理知识库检索接口， 与 Pipeline Step 2 集成（RAG context 传入需求分析步骤）。
为什么改 原知识库模块散落在前端，与 Pipeline 集成困难； 统一移至服务端后，Pipeline 各步骤可按需检索知识库而不需通过前端中转。
改完效果 知识库上下文可作为 Step 2 需求分析的参考输入，提升需求理解准确性。

④ 用例生成页 & 契约页交互优化TestCaseGenerationPage.tsx / QualityContractsPage.tsx · 大幅改动

改了什么 用例生成页增加 Pipeline 进度展示（代码分析进度条、步骤状态提示）； 契约页（QualityContractsPage）497 行大改，支持流式渲染和草稿编辑； 新增 inputSnapshotStore 保存生成时的输入快照，支持复现上一次生成。
为什么改 多步 Pipeline 执行时间较长（尤其代码预分析步），用户需要可见的反馈； 输入快照避免用户每次手动重填参数。
改完效果 用户可在生成过程中看到实时进度，操作感更流畅； 一键复用上次输入配置，减少重复操作成本。
