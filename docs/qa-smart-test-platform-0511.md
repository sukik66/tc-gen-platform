# QA 智能测试平台（72-Agents）— 设计与实践

> 基于 LangGraph 有向图 + MCP 工具协议 + RAG 知识库的需求-代码融合测试用例自动生成系统。
> 适用于有需求文档和/或代码仓库的软件项目（已在 Lua/C# 游戏项目中落地验证）。

---

## 1. 解决什么问题

| 痛点 | 传统做法 | 本方案 |
|------|---------|--------|
| 需求文档和代码变更之间缺乏关联分析 | 测试人员分别阅读需求和代码，手动关联 | AI 同时分析需求文档和 Git 代码变更，自动交叉生成测试点 |
| 代码变更涉及多文件时分析效率低 | 串行阅读每个变更文件，容易遗漏 | Fan-out 并发架构，每个变更文件独立 LLM 分析，并行处理 |
| 历史测试经验和风险知识分散在人脑中 | 依赖资深测试人员的个人经验 | RAG 知识库检索历史风险案例和测试经验，自动注入分析上下文 |
| 测试报告格式不统一，手动排版耗时 | 每人一套格式，整理报告占大量时间 | 自动组装结构化 Markdown 报告（含需求分析 + 风险 + 用例 + 流程图） |

**一句话说明**：上传需求文档 + 输入任务 ID → AI 拉取代码变更 → 逐文件并发分析 → 知识库检索 → 需求综合 → 生成测试点 + 流程图 → 组装报告。

## 3. 核心流程：case_graph 智能体

### 9 节点有向图

```
输入处理 (node_01)
  │
  ▼
代码变更准备 (node_02a)
  │
  ├─── file_groups 非空 ──→ ⚡ Fan-out 并发区
  │                          │
  │                    逐文件代码分析 (node_02b) ×N
  │                          │
  │                          ▼
  └─── file_groups 为空 ──→ 文件分析汇总 (node_02c) ←── Fan-in
                             │
                             ▼
                    知识库检索 (node_03)
                             │
                             ▼
                    需求理解综合 (node_04)
                             │
                             ▼
                    测试点生成 (node_06)
                             │
                             ▼
                    流程图生成 (node_07)
                             │
                             ▼
                    报告组装 (node_08)
                             │
                             ▼
                    保存结果 (node_09)
```

### 各节点详解

#### Node 01 · 输入处理

```
用户输入（前端 JSON）
  │
  ├── documents: 需求文档路径列表
  ├── tasks: 任务 ID / JIRA Key / 分支名
  └── extra_info: 补充说明
  │
  ▼
┌────────────────────────────────────────────────┐
│ 1. validate_documents — 路径安全、扩展名白名单   │
│    (.pdf/.docx/.txt/.md/.doc)、≤10MB            │
│ 2. validate_tasks — 3-8位数字 / JIRA Key /      │
│    分支名模式匹配                                │
│ 3. sanitize_extra_info — 去除注入风险            │
│ 4. 调用 MCP 文档解析工具读取文档内容              │
│ 5. 初始化 State，status = in_progress            │
└────────────────────────────────────────────────┘
```

#### Node 02a · 代码变更准备

```
任务 ID / 分支名
  │
  ▼
┌────────────────────────────────────────────────────┐
│ 1. 根据 Task ID 从 Git 仓库拉取 log & diff          │
│ 2. 按文件路径分组 → file_groups                      │
│ 3. 统计代码变更量 → code_stats（增删行数、文件数）   │
│                                                      │
│ 路由决策：                                           │
│ ├── 有 file_groups → Fan-out 并发分析每个文件        │
│ └── 无（无任务/找不到提交）→ 启用 fallback 路径      │
│     （用文档内容替代代码变更，不中断流程）             │
└────────────────────────────────────────────────────┘
```

#### Node 02b · 逐文件代码分析（Fan-out 并发 ×N）

```
单个文件组（diff 内容）
  │
  ▼
┌──────────────────────────────────────────────┐
│ 独立 LLM 调用，提取：                          │
│ ├── 关键字段（≤40 条/文件）                    │
│ ├── 关键函数（≤40 条/文件）                    │
│ └── 关键代码片段（≤3 条/文件）                 │
│                                              │
│ 约束：                                       │
│ ├── 单文件 diff 上限 40,000 字符（超出截断）   │
│ ├── 超大 diff（>35,000 字符）改用结构摘要模式  │
│ ├── 单文件超时 300 秒                         │
│ └── LLM 调用失败 → 该文件降级，不阻断其他     │
└──────────────────────────────────────────────┘
  │
  ▼
追加到 file_analyses（operator.add 合并）
```

#### Node 02c · 文件分析汇总（Fan-in）

将所有 `file_analyses` 合并为统一的 `code_analysis`。若 `file_analyses` 为空，使用 `fallback_code_analysis`。

#### Node 03 · 知识库检索

```
三种 RAG 模式：
┌──────────────────────────────────────────────────────┐
│ risk_analysis（默认）                                  │
│   检索历史风险案例、测试经验，辅助识别高风险点          │
│                                                      │
│ requirements_analysis                                 │
│   检索策划/设计文档，作为需求规格参考                   │
│                                                      │
│ custom                                                │
│   用户自定义知识库语义，LLM 自主组合输出               │
└──────────────────────────────────────────────────────┘

输出：risk_analysis 文本 + 动态章节标题（rag_section_title）
降级：RAG 不可达 → 跳过，仅用代码分析结果继续
```

#### Node 04 · 需求理解综合

结合代码变更分析、文档内容、RAG 检索结果，生成需求理解报告（`requirement_report`）。支持通过 `requirement_instruction` 注入提示词样式预设。

#### Node 06 · 测试点生成

```
两种分组策略：
┌──────────────────────────────────────────────────────┐
│ 用户自定义（test_case_instruction 非空）              │
│   严格按用户指定的测试方法名作为一级标题分组           │
│   禁止 LLM 自行发明分组                              │
│                                                      │
│ 智能自主分组（默认）                                  │
│   基于需求特征、风险等级、业务模块自主决策分组维度     │
└──────────────────────────────────────────────────────┘

输出：test_points 列表，最多 100 条
```

#### Node 07 · 流程图生成

为关键测试场景生成 Mermaid 格式流程图，输出 `flowcharts`（含 `title` + `mermaid_code`）。支持自动降级（节点过多时降为表格或 Callout 格式）。

#### Node 08-09 · 报告组装与保存

```
┌──────────────────────────────────────────────┐
│ 拼装最终 Markdown 报告：                       │
│ ├── 需求分析（含关键指标统计）                 │
│ ├── 风险分析（知识库检索 + 代码推断）          │
│ ├── 代码变更摘要（文件变更统计表）             │
│ ├── 系统可视化（Mermaid 流程图）              │
│ └── 测试用例（分组结构化呈现）                 │
│                                              │
│ 落盘 → report_path + download_url            │
│ 状态 → completed                              │
└──────────────────────────────────────────────┘
```

## 4. MCP 工具链

系统通过 MCP（Model Context Protocol）协议将外部能力封装为 Agent 可调用的工具：

| MCP 服务 | 端口 | 提供的工具 | 用途 |
|---------|------|----------|------|
| 文档解析 MCP | 6004 | `analyze_document` | 解析 PDF/DOCX/TXT/MD/DOC，提取文本和图片（含 VLM 视觉分析） |
| Git MCP | 6006 | `list_repos` / `set_cwd` / `log` / `diff` / `task_diff` / `show_file` / `stat` 等 | Git 仓库操作：提交日志、代码 diff、文件内容读取 |
| RAG MCP | 6005 | `search_risk_cases` | 知识库向量检索：历史风险、测试经验、需求规格 |

**工具装配**：通过 `config.env` 的 `CASE_GRAPH_TOOLS` 配置 Agent 可用的工具集（逗号分隔），默认为 `list_uploads,analyze_document,search_risk_cases,git_tools`。

**工具管理器**（`tool_manager.py`）：单例模式 + 线程安全，统一管理 Git 工具集和文档工具集的生命周期。

### 检索参数

| 参数 | 默认值 | 说明 |
|------|-------|------|
| 检索模式 | mix | local / global / hybrid / naive / mix / bypass |
| 实体 top_k | 60 | 实体检索数量 |
| 文本块 top_k | 10 | 文本块检索数量 |
| 最大 Token | 8000（总）/ 3000（实体）/ 3000（关系） | 返回给 Agent 的上限 |
| 请求超时 | 120s / 流式 300s | - |
| 引用来源 | 开启 | 响应中附带引用 |

### 知识库管理

- 支持多知识库（通过 `KNOWLEDGE_BASE_NAMES` 配置，如 `72,71`）
- LightRAG WebUI 提供可视化管理界面（`:6003`）
- 独立的 RAG 控制台（`rag_console/main.py`）用于启停 RAG 服务
- 文档导入：将测试经验、历史风险、需求文档等注入知识库

## 8. 质量契约

每个关键阶段有明确的输入输出约束和降级策略：

| 阶段 | 输入约束 | 输出约束 | 降级策略 |
|------|---------|---------|---------|
| 输入处理 | 路径安全、扩展名白名单、≤10MB | doc_content 已解析 | 验证失败 → status=failed，后续跳过 |
| 代码变更准备 | Task ID 有效、GIT_REPO_PATH 已配置 | file_groups 按文件分组 | 找不到提交 → fallback，用文档替代 |
| 文件并发分析 | 单文件 diff ≤40,000 字符 | 关键字段/函数/片段 | 单文件 LLM 失败 → 该文件降级，不阻断 |
| 知识库检索 | RAG 服务可达 | risk_analysis 文本 | RAG 不可达 → 跳过，继续用代码分析 |
| 测试点生成 | code_analysis + requirement_report | test_points ≤100 条 | 超 100 条 → 截断 |
| 最终报告 | 所有中间产出已写入 State | Markdown 完整 + 可下载 | failed 节点标注 skipped |

**核心原则**：诚实优先——信息不足时明确写出"信息不足：需提供……"，并指出缺失项。不编造文件、函数、配置或数据。

## 9. 配置体系

### config.env 关键配置

| 配置组 | 关键项 | 说明 |
|--------|-------|------|
| LLM | `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` / `LLM_TEMPERATURE` | 智能体分析节点使用的大模型 |
| VLM | `VLM_API_KEY` / `VLM_MODEL` | 文档图片视觉分析模型 |
| Git | `GIT_REPO_PATH` | 要分析的代码仓库绝对路径 |
| Git Diff 过滤 | `GIT_DIFF_INCLUDE_PATTERNS` / `GIT_DIFF_EXCLUDE_PATTERNS` | 文件类型白名单 / 目录黑名单 |
| Git Diff 限制 | `GIT_DIFF_MAX_CHARS` / `GIT_DIFF_MAX_CHARS_PER_FILE` | 总 diff 上限 80 万字符 / 单文件 4 万字符 |
| RAG | `RAG_ENABLED` / `KNOWLEDGE_BASE_NAMES` | 是否启用知识库 / 知识库名称列表 |
| 端口 | `AGENTS_PORT` ~ `AGENT_UI_PORT` | 各服务端口，修改后自动跟随 |
| 工具 | `CASE_GRAPH_TOOLS` | Agent 可用工具列表 |

### 模型预设

支持保存多套模型配置预设（`data/presets.json`），可在前端一键切换：
- LLM 模型与地址
- VLM 模型与地址
- Git 仓库路径
- Diff 过滤规则
- RAG 开关与知识库名称

### 提示词样式

支持自定义提示词风格预设（`data/prompt_styles.json`）：
- `test_case_instruction`：测试分组策略（约束 LLM 输出分组结构）
- `requirement_instruction`：需求分析指令
- `rag_instruction`：知识库检索指令（已废弃，保留兼容）
- `rag_mode`：检索模式选择

## 10. 报告输出格式

### 报告结构

```
📊 测试报告 · 任务 #TaskID
├── 需求分析
│   ├── 关键指标（涉及文件数、代码变更量、风险等级、测试点数）
│   ├── 背景与目标
│   ├── 业务规则
│   ├── 数据模型
│   ├── 状态与流程
│   ├── 配置与热更
│   ├── 前后端与协议
│   ├── GM 与测试接口
│   ├── 风险评估（分级：🔴高/🟡中/🟢低）
│   └── 影响面分析
├── 风险分析（知识库）
│   ├── 配置变更风险
│   ├── 边界与周期风险
│   ├── 协议与前后端一致性风险
│   └── 运维事件与数据一致性风险
├── 代码变更摘要
│   ├── 文件变更统计表
│   └── 详细分析（逐文件）
├── 系统可视化
│   └── Mermaid 流程图
└── 测试用例
    ├── 分组 1（按方法或模块分组）
    │   ├── 子分组
    │   │   └── 用例条目（操作步骤 + 预期结果 + 测试数据 + 状态）
    │   └── ...
    └── 分组 N
```

### 用例格式

每条用例包含：
- **操作步骤**：具体可执行的操作描述
- **预期结果**：可判定 pass/fail 的预期行为
- **测试数据**：相关的配置项、参数值、模拟条件
- **状态**：⏳（待执行）

## 11. 与 ai-test-platform 的对比

两个平台解决不同层面的问题，互为补充：

| 维度 | QA 智能测试平台（72-Agents） | ai-test-platform |
|------|--------------------------|-----------------|
| 核心思路 | LangGraph 有向图编排多步骤 Agent | 提示词工程 + 单次/流式 LLM 调用 |
| 输入 | 需求文档 + 任务 ID（Git 自动关联） | 需求文档 + 可选代码变更面板 |
| 代码分析 | 自动从 Git 拉取 diff，逐文件并发 LLM 分析 | 手动选择仓库/分支/时间范围，代码注入提示词 |
| 知识库 | LightRAG（知识图谱 + 向量，本地 Embedding） | LightRAG HTTP 客户端（检索注入） |
| 输出 | Markdown 报告（需求分析 + 风险 + 用例 + 流程图） | 结构化 JSON 用例数组（11 字段） |
| 视图 | Markdown 渲染 + Mermaid | 脑图 / 卡片 / 表格三视图 |
| 导出 | Markdown 报告下载 | Excel / XMind / Checklist |
| 编辑 | 不支持用例编辑（报告为最终产出） | 双击内联编辑 + 新增/删除 |
| 用例库 | 无 | 项目→模块→用例 + 用例集 |
| 多模型 | 单通道（config.env 配置） | 9 厂商通道前端切换 |
| 部署 | 多进程（6 个服务 + 控制面板） | 单进程（npm run dev 双服务） |
| 技术栈 | Python (LangGraph/FastAPI) + Next.js | Node.js (Express) + React (Vite) |

## 12. 关键设计决策

| 决策 | 选了什么 | 为什么 |
|------|---------|--------|
| Agent 编排 | LangGraph StateGraph | 有向图天然支持 Fan-out/Fan-in 并发，节点间状态显式传递 |
| 工具协议 | MCP | 工具与 Agent 解耦，可独立部署和替换 |
| 代码分析粒度 | 逐文件并发 | 大型任务多文件变更时串行太慢，且单文件 diff 可精确截断 |
| 知识库 | LightRAG + 本地 Ollama Embedding | 全本地部署，数据不外传；知识图谱比纯向量检索更精准 |
| 文档解析 | docling + VLM | docling 处理文本，VLM 处理文档中的图片/表格 |
| 降级策略 | 每个节点独立降级 | 单文件失败 / RAG 不可达不阻断整体流程 |
| 报告格式 | Markdown + Mermaid | 通用、可版本控制、可渲染 |
| 服务管理 | 控制面板一键启停 | 6 个服务手动管理太复杂 |
| 诚实原则 | System Prompt 最高优先级 | 信息不足时宁可留空也不编造 |
| 分组策略 | 用户自定义 + AI 自主双模式 | 标准化测试场景需要固定分组，探索性场景需要 AI 灵活决策 |
