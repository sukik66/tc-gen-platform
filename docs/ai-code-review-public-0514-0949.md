# AI 代码走查系统 — 设计与实践

> 基于 LLM + 确定性工具链的需求-代码一致性自动验证方案。
> 适用于有明确需求文档的软件项目（已在 Unity C# 游戏项目中落地验证）。

---

## 1. 系统定位

代码提交后，结合 AI 能力执行一轮自动化走查，快速暴露明显的需求点遗漏和代码隐患（附带发现），为人工 review 提供聚焦线索。

---

## 2. 整体流程

### 流程总览

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                                                                              │
│   📄 需求文档                                                                │
│   (.docx/.md)                                                                │
│       │                                                                      │
│       ▼                                                                      │
│   ┌─────────────────────────────────────────────────────────────┐            │
│   │  Phase 0: 环境初始化  [脚本]                                 │            │
│   │  → 代码新鲜度检测（对比缓存中已记录文件的修改时间和大小，   │            │
│   │    标记变更文件和新增文件）                                   │            │
│   │  → 依赖图谱加载（优先探测编译器生成的索引文件，              │            │
│   │    未找到则脚本自建）                                        │            │
│   │  → 历史反馈加载（读取上次走查的人工标注）                    │            │
│   └─────────────┬───────────────────────────────────────────────┘            │
│                 ▼                                                             │
│   ┌─────────────────────────────────────────────────────────────┐            │
│   │  Phase 1: 契约提取  [LLM]                                   │            │
│   │  → 提取质量契约 + SR 子要求拆解                              │            │
│   └─────────────┬───────────────────────────────────────────────┘            │
│                 ▼                                                             │
│   ┌─────────────────────────────────────────────────────────────┐            │
│   │  Phase 1.5: AST 结构化扫描  [脚本]                          │            │
│   │  → 代码结构分析（8条自定义规则）                             │            │
│   └─────────────┬───────────────────────────────────────────────┘            │
│                 ▼                                                             │
│   ┌─────────────────────────────────────────────────────────────┐            │
│   │  Phase 1.7: SR 搜索预执行  [脚本]                           │            │
│   │  → 脚本先把所有 SR 关键词拿去代码库搜一遍                   │            │
│   │  → 能直接出结论的（禁止类/运行时类）脚本自动判定            │            │
│   │  → 其余 SR 把搜到的真实代码片段打包交给 AI 后续判定         │            │
│   └─────────────┬───────────────────────────────────────────────┘            │
│                 ▼                                                             │
│   ┌─────────────────────────────────────────────────────────────┐            │
│   │  Phase 2: 代码走查  [LLM]                                   │            │
│   │  → 搜索 → 阅读 → 判定（仅处理脚本无法自动判定的 SR）       │            │
│   └─────────────┬───────────────────────────────────────────────┘            │
│                 ▼                                                             │
│   ┌─────────────────────────────────────────────────────────────┐            │
│   │  Phase 2.5: Evidence 校验 + 修正循环  [脚本 + LLM]          │            │
│   │  → 磁盘验证 → 失败项附带真实代码内容 → LLM 修正 → 重验      │            │
│   │  → 最多2轮；仍失败则标记未验证 + 视情况降级判定              │            │
│   └─────────────┬───────────────────────────────────────────────┘            │
│                 ▼                                                             │
│   ┌─────────────────────────────────────────────────────────────┐            │
│   │  Phase 3: 报告生成  [LLM + 脚本]                            │            │
│   │  → 输出 results.json（AI 数据源）+ 走查报告.md（人读）      │            │
│   │  → 脚本自动校验报告完整性                                    │            │
│   └─────────────────────────────────────────────────────────────┘            │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

**核心设计原则**：能用脚本确定性完成的步骤（搜索、扫描、校验），绝不让 LLM 自由发挥。LLM 只负责真正需要语义理解的部分（契约提取、代码阅读判定）。

### Phase 1 契约提取 — "从需求文档里提炼出要检查什么"

```
需求文档
  │
  ▼
┌──────────────────────────────────────────────────────────┐
│ 1. 读取文档内容                                           │
│ 2. 提取「质量契约」= 一条条可检查的业务规则                │
│    例："玩家死亡后 3 秒内在最近检查点复活"                  │
│ 3. 将复杂规则拆成原子级「子要求 SR」                       │
│    例：SR-1 "死亡后触发复活倒计时"                         │
│        SR-2 "倒计时 3 秒"                                  │
│        SR-3 "复活点为最近检查点"                            │
│ 4. 给每个 SR 标注验证类型 checkType（见下文）              │
└──────────────────────────────────────────────────────────┘
  │
  ▼
📋 契约库 JSON
```

**质量契约 vs 测试用例**：

| | 质量契约 | 测试用例 |
|---|---------|---------|
| 描述 | 「系统应该满足什么」 | 「怎么一步步去验证」 |
| 粒度 | 业务规则（跨场景不变量） | 具体操作步骤 |
| 内容 | 不含文件路径、接口 URL | 包含具体执行细节 |

## 3. 核心设计

### 3.1 子要求拆解 (Sub-Requirement, SR)

一条业务规则可能包含多个可独立验证的断言。

**为什么要拆**：如果整体判定，AI 可能因为 SR-1 通过了就整条判 pass，漏掉 SR-2 其实没实现。拆开后每个 SR 独立判定，任一 fail → 整条 fail。

### 3.2 checkType 路由（共 5 种）

```
                        子要求 SR
                           │
                     checkType 是什么？
                           │
         ┌────────┬────────┼────────┬────────┐
         ▼        ▼        ▼        ▼        ▼

   grep_existence  grep_forbidden  ast_pattern  llm_semantic  runtime_only
   "功能存不存在"   "禁止的东西      "代码结构     "需要读懂     "只能运行
                    有没有出现"       匹配"        代码语义"     时才能看出"
```

| # | checkType | 判定方式 | 举例 |
|---|-----------|---------|------|
| 1 | `grep_existence` | 脚本预搜索 + LLM 确认 | "复活功能" → 搜 `Respawn` |
| 2 | `grep_forbidden` | **脚本自动判定**：搜到 = fail | "不做弹簧平滑" → 搜 `SmoothDamp` |
| 3 | `ast_pattern` | AST 工具自定义规则 | "事件 += 有没有对应 -=" |
| 4 | `llm_semantic` | AI 判定（受防护规则约束） | "死亡后倒计时逻辑是否正确" |
| 5 | `runtime_only` | **脚本自动判定**：直接标 uncertain | "动画播放是否流畅" |

**设计理念**：能用程序确定性判定的（1/2/3/5），绝不让 AI 来判。AI 只负责真正需要语义理解的部分（4）。

### 3.3 判定防护规则体系

| 层级 | 规则名 | 通俗解释 | 防止什么 |
|------|--------|---------|---------|
| 1 | Pass 防护铁律 | 想判通过？先证明每个子要求都有实打实的代码证据 | 防止虚高通过 |
| 2 | Fail 推定规则 | 关键词搜遍全库确实 0 结果 → 判 fail | 让真缺失的功能被准确标记 |
| 2.1 | 强制豁免自检 | 判 fail 前排除 3 种假阴性 | 防止误杀 |
| 2.2 | 空实现条款 | 方法存在但 body 为空 → 仍 fail | 防止空壳方法被当已实现 |
| 3 | 否决铁律 | 发现和需求矛盾的证据 → 绝不判 pass | 防止矛盾证据被忽略 |

**强制豁免自检的 3 种检查**：

| # | 检查场景 | 举例 |
|---|---------|------|
| A | **通用机制实现** | 没有专属方法，但通用 OnDrop 里有位置重置逻辑 |
| B | **回调/事件模式** | 没有 anyClick 方法，但通过回调委托实现 |
| C | **配置驱动** | 代码里没设置颜色，但 UI 资产里已配置高亮色 |

```
搜索关键词全库 0 命中 → 准备判 fail
  │
  ├─ A/B/C 任一找到 → 豁免为 uncertain
  │
  └─ 三项全部没找到 → 确认判 fail
       └─ 但方法体为空 → 空实现条款 → 仍然 fail
```

### 3.4 附带发现与违规性分级

| 违规性 | 含义 | 后续动作 |
|--------|------|---------|
| **违规** | 与需求某条明确约束矛盾 | 升级为新契约 → fail |
| **潜在违规** | 看起来不对但无直接矛盾条款 | 需确认 |
| **建议改进** | 代码质量问题 | 不阻塞 |
| **待确认** | 需运行时验证 | 下次测试关注 |

### 3.5 Evidence 程序化验证 + 修正循环

```
走查判定完成
  │
  ▼
脚本对每条 evidence 做 3 级磁盘验证
├─ 文件路径是否真实存在
├─ 行号是否在文件范围内
└─ 方法名是否出现在该行号附近
  │
  ▼
失败项附带修正信息
├─ actual_content: "这一行的真实内容是 xxx"
├─ suggested_paths: "文件可能在 A/B/C 路径"
  │
  ▼
LLM 据此修正 → 脚本重新验证（最多2轮）
  │
  ▼
2 轮后仍失败？→ 兜底规则：
├─ 全部 evidence 失败 → 判定降级为 uncertain
└─ 部分 evidence 失败 → 判定不变，报告标注未验证项
```

## 4. 工具链架构

### 工具分类

| 工具 | 来源 | 做什么 |
|------|------|--------|
| **Grep** | IDE 内置 | 代码库全文搜索 |
| **SR 预搜索脚本** | 自主开发 | 批量关键词搜索 + 确定性 SR 自动判定 |
| **AST 扫描脚本** | 自主开发 | 代码结构分析（8 条自定义规则） |
| **证据验证脚本** | 自主开发 | 检查证据真伪 + 提供修正信息 |
| **依赖图谱** | 编译器 / 自建 | 类间依赖关系 + 文件结构索引 |
| **映射缓存脚本** | 自主开发 | "模块→代码文件"缓存 |
| **报告校验脚本** | 自主开发 | 检查报告必要区段是否齐全 |

> **设计原则**：AI 擅长理解语义但不可靠，脚本不懂语义但确定性高。用脚本约束 AI 不擅长的部分。

### AST 自定义规则库（8 条）

| 规则 | 检测内容 | 用途 |
|------|---------|------|
| 空方法体 | 方法体为空 | 直接支撑空实现条款判定 |
| 事件订阅配对 | += / -= 赋值 | 找出只订阅未取消的事件 |
| 协程无 yield | IEnumerator 无 yield | 未完成的协程实现 |
| GetComponent 调用 | GetComponent 调用点 | null 安全分析 |
| 单例模式 | 静态 Instance 属性 | 设计模式标签 |
| ScriptableObject | SO 配置类 | 设计模式标签 |
| 对象池使用 | ObjectPool 调用 | 设计模式标签 |

### 依赖图谱双源架构

| 项目条件 | 图谱来源 | 精度 |
|---------|---------|------|
| 有编译器索引文件 | 编译器生成的结构化索引 | 高（含继承/接口/泛型） |
| 无编译器索引文件 | 脚本正则扫描自建 | 低（仅正则匹配） |

### 产出文件与读者分工

| 文件 | 格式 | 读者 | 定位 |
|------|------|------|------|
| **走查结果 JSON** | JSON | **AI**（下次走查/回归对比/反馈统计） | 唯一机器数据源，包含全部结构化字段 |
| **走查报告 .md** | Markdown | **人**（策划/开发/测试） | 排版摘要，聚焦判定结论和证据要点 |

> AI 下游任务应读 JSON 数据源，不应解析 .md 报告。

### 全部数据文件说明

| 文件 | 一句话解释 | 写入方 | 读者 | 保留策略 |
|------|-----------|--------|------|---------|
| **契约库 JSON** | 从需求文档提取的检查规则清单 | Phase 1 | Phase 1.7 + Phase 2（AI） | 永久保留 |
| **走查结果 JSON** | 完整机器数据（判定/证据/附带发现/AST摘要/验证详情） | Phase 2 + 2.5 | AI 下游任务 | 永久保留 |
| **走查报告 .md** | 给人看的排版报告 | Phase 3 | 人工阅读 | 永久保留 |
| **映射缓存 JSON** | "模块 → 代码文件"对应关系 | 映射脚本 | 下次走查加速 | 自动更新 |
| **AST 扫描结果** | 本次扫描原始结果（快照） | AST 脚本 | 映射脚本 | 每次覆盖 |
| **依赖图谱缓存** | 类间依赖 + 文件结构索引 | init 脚本 | Phase 2 走查 | 变更后更新 |
| **反馈数据** | 人工标注的"准确/误判/遗漏" | 人工录入 | init → Few-shot | 持续积累 |

## 5. 仓库支持

系统支持同时接入多个代码仓库。走查时根据契约内容自动选择相关仓库进行搜索。

支持的仓库类型：Git、Plastic SCM 等常见版本管理工具。当前已在 2 个不同项目（5 个仓库）上验证通过。

## 6. 踩过的坑与优化经验

### 6.1 AI 判定不稳定 → 子要求拆解 + 确定性分流

**问题**：不同 LLM 模型对同一需求走查差异大。**解法**：规则拆为原子级 SR → 程序确定性判的不让 AI 判 → 防护规则硬约束。

### 6.2 虚假 Pass → Pass 防护铁律

**问题**：搜到文件名就判 pass。**解法**：每个 SR 必须有 ≥1 条正面 evidence。

### 6.3 判定偏软 → Fail 推定规则

**问题**：全库 0 命中也不敢判 fail。**解法**：充分搜索后确认缺失 → 判 fail。

### 6.4 假 Fail → 豁免自检 / 6.5 豁免过度 → 空实现条款

**两者互制**：豁免自检（防误杀）+ 空实现条款（防过度豁免）。

### 6.6 否定式约束漏检 → grep_forbidden

**解法**：独立 checkType，脚本自动判定。

### 6.7 AI 证据幻觉 → Evidence 验证 + 修正循环

**解法**：脚本 3 级磁盘验证 → 失败项附真实代码内容 → LLM 修正 → 重验 → 仍失败则标记 + 降级。

### 6.8 附带发现被忽视 → 违规性分级

**解法**：4 级违规性标注。

### 6.9 AST 确定性判定不足 → 自定义规则库

**解法**：8 条规则，改为 AST 节点类型 + 正则匹配。**踩坑**：pattern 语法对 C# Allman 风格兼容性不足。

### 6.10 LLM 判定不一致 → Few-shot 校准

**解法**：3 个典型示例。

### 6.11 AI 遗忘搜索结果 → 证据预采集

**解法**：将搜索产出结构化为候选列表，判定时从列表引用。

### 6.12 LLM 不执行指令 → 脚本硬编码

**问题**：LLM 遵从度不稳定，经常跳步。**解法**：Python 统一入口脚本，将确定性步骤硬编码。

### 6.13 LLM 搜索编造行号 → SR 搜索预执行

**解法**：脚本批量搜索输出真实 file/line/snippet，LLM 从中选取。

### 6.14 自建依赖图谱精度低 → 双源架构

**解法**：优先编译器索引，无则降级自建。

## 8. 走查报告解读

### 报告结构

```
📊 走查报告
├── 总览表（契约数量、通过/违规/存疑统计、工具状态）
├── 走查详情（逐条契约）
│   ├── 规则 + 边界提示
│   ├── 子要求判定表（每个 SR 的独立结论）
│   ├── 汇总判定
│   ├── 证据列表（文件、行号、方法名、说明）
│   ├── 缺口说明
│   └── 附带发现（含违规性分级）
└── 未走查契约（非 code_review 类型）
```

### 判定含义

| 判定 | 含义 | 行动 |
|------|------|------|
| ✅ pass | 找到充分证据支撑规则成立 | 仅作参考，建议人工抽查 |
| ❌ fail | 确认功能缺失或与规则矛盾 | **核心产出**，需开发确认/修复 |
| ❓ uncertain | 证据不足以判定 | 需人工确认或运行时验证 |

- ✅ SR 搜索预执行（确定性 SR 脚本自动判定）
- ✅ 依赖图谱双源架构（编译器索引优先）
- ✅ 代码新鲜度检测
- ✅ 反馈机制框架

### 规划中

| 项目 | 内容 | 预期收益 |
|------|------|---------|
| 补全走查结果 JSON Schema | 确保 AI 数据源包含全部结构化数据 | AI 下游任务不再解析 .md |
| 反馈闭环完善 | 更多"准确/误判/遗漏"标注回注 | 持续自动纠偏 |
| 增量走查 | 只重查变更文件相关契约 | 大幅减少回归走查时间 |

## 10. 适用场景与局限性

### 适合

- 有明确需求文档的项目
- 代码可被文本搜索的项目
- 需要高频回归核查的场景
- 多仓库交叉验证

### 不适合 / 有局限

| 场景 | 原因 |
|------|------|
| 纯运行时行为验证 | 代码走查无法覆盖 |
| 无需求文档或需求极度模糊 | 无法提取有效契约 |
| 高度动态的配置表/数据驱动逻辑 | 代码中看不到最终行为 |
| 第三方 SDK / 加密代码 | 无法搜索和阅读 |

## 11. 关键设计决策总结

| 决策 | 选了什么 | 为什么 |
|------|---------|--------|
| 判定单元 | 原子级子要求（SR） | 防止复合规则下的子项遗漏 |
| 搜索策略 | 脚本预搜索 + AI 补充 | 确定性 > AI 理解力，避免编造行号 |
| 判定约束 | 硬编码防护规则 | AI 有判定偏好（偏 pass），需要纠偏 |
| 证据校验 | 脚本磁盘验证 + 修正循环 | AI 幻觉不可忽视，需当场修正 |
| 报告分工 | JSON = AI 读，.md = 人读 | 各自格式优化，互不干扰 |
| 否定约束 | 独立 checkType，脚本自动判定 | 二值判定，不应进入语义分析 |
| 依赖图谱 | 编译器索引优先 | 精度高且速度快 |
| 流程控制 | 脚本硬编码 | LLM 对长指令遵从度不稳定 |
