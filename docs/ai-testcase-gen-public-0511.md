# AI 测试用例生成系统 — 设计与实践

> 基于 LLM + 结构化提示词工程 + 多通道模型适配的需求驱动测试用例自动生成方案。
> 适用于有需求文档的软件项目（已在 Unity C# 游戏项目中落地验证）。

---

## 1. 解决什么问题

| 痛点 | 传统做法 | 本方案 |
|------|---------|--------|
| 需求文档写完后，手动拆解测试用例耗时且因人而异 | 测试人员逐条阅读需求，凭经验编写用例 | AI 自动从需求文档生成结构化用例，覆盖主路径 + 异常 + 边界 |
| 不同测试人员对同一需求的用例覆盖度差异大 | 依赖个人经验和测试方法论掌握程度 | 将 ISTQB 方法论（等价类、边界值、判定表等）编码进提示词，保证方法论层面的一致性 |
| 需求变更后用例回归更新成本高 | 手动对照新旧需求修改用例 | 上传新版文档重新生成，几分钟出完整用例集 |
| 测试深度难以灵活调整 | 切换测试阶段时需手动删减/补充用例 | 三档详细程度（策划验收 / 开发自测 / QA 测试），同一文档一键切换不同粒度 |

**一句话说明**：上传需求文档 → 配置生成参数 → AI 生成结构化用例 → 多视图展示与编辑 → 导出交付。

### Phase 1 文档解析 — "把各种格式的文档变成纯文本"

```
用户上传文件（支持多文件、拖拽）
  │
  ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. 浏览器端解析（不经服务端）                                  │
│    - .docx → mammoth 提取文字                                 │
│    - .pdf  → pdf.js 提取文字（扫描版可能无字）                │
│    - .xlsx → xlsx 库提取表格内容                              │
│    - .md/.txt/.csv/.json → 直接读取                          │
│    - 图片 → Tesseract.js OCR（中英双语，串行处理）            │
│ 2. 为每个文件设置「文档角色」（6 种可选）                      │
│    主需求 / 附件 / 关联需求 / 参考用例 / 旧版 / 新版          │
│ 3. 拖拽排序（列表自上而下 = 进入模型的阅读顺序）              │
│ 4. 生成前门槛：至少一份文件解析成功                            │
└──────────────────────────────────────────────────────────────┘
  │
  ▼
📋 文档文本 + 角色标注 + 排序
```

**文档角色的意义**：不同角色在提示词中有不同的引导语，告诉 AI 这份材料应该怎么用：

| 角色 | 提示词中的引导 | 适用场景 |
|------|-------------|---------|
| 主需求 | "用例设计的主要依据" | 详设文档、PRD |
| 附件 | "辅助理解主需求" | UI 稿、配置说明 |
| 关联需求 | "与主需求交叉验证" | 前置模块的需求文档 |
| 参考用例 | "可作覆盖参考，勿机械照搬" | 历史版本用例 |
| 旧版/新版 | "用于对比与回归" / "与旧版差异为重点" | 版本迭代场景 |

## 3. 核心设计

### 3.1 双通道生成架构

系统提供两条独立的生成通道，适应不同场景：

```
                     ┌─────────────────────────────────────────────┐
                     │           用户选择生成方式                    │
                     │                                              │
                     │   ┌──────────────┐   ┌──────────────────┐  │
                     │   │  API 生成     │   │  Cursor 辅助     │  │
                     │   │ （一键自动）  │   │ （复制粘贴手动）  │  │
                     │   └──────┬───────┘   └────────┬─────────┘  │
                     │          │                     │             │
                     └──────────│─────────────────────│─────────────┘
                                ▼                     ▼
                     ┌──────────────────┐  ┌──────────────────────┐
                     │ 前端 → 后端 API   │  │ 前端生成提示词        │
                     │ POST /api/...     │  │ → 复制到剪贴板       │
                     │ 后端调用 LLM      │  │ → 粘贴到 Cursor 对话  │
                     │ SSE 流式返回       │  │ → 模型返回 JSON      │
                     │ 自动规范化         │  │ → 粘贴回页面解析      │
                     └──────────────────┘  └──────────────────────┘
```

| 维度 | API 生成 | Cursor 辅助 |
|------|---------|------------|
| 前提 | 服务端配置了 LLM API 密钥 | 无需密钥，只需 Cursor IDE |
| 操作 | 一键生成，SSE 流式实时展示 | 三步：复制提示词 → 粘贴到 Cursor 聊天 → 粘贴返回 JSON |
| 模型 | 9 厂商通道可切换 | Cursor 内置模型 |
| 适用 | 团队使用、批量生成 | 个人使用、无密钥场景、快速体验 |

**设计理念**：密钥仅在服务端持有，浏览器不直连模型。无密钥时仍可通过 Cursor 辅助通道使用全部功能，不阻塞体验。

### 3.2 三档详细程度

同一份需求文档，通过切换详细程度，自动调整生成策略：

| 档位 | 标签 | 最低条数 | 弹性上限 | 非主流程占比 | 每步用例数 | 适用场景 |
|------|------|---------|---------|------------|----------|---------|
| 策划验收 | 轻量 | 12 | 28 | ≥25% | 1~2 条 | 快速验证业务闭环 |
| 开发自测 | 标准 | 22 | 48 | ≥35% | 2~3 条 | 覆盖正常路径 + 常见异常 |
| QA 测试 | 超详细 | 36 | 90 | ≥45% | 3~5 条 | 全量：边界、异常、安全、兼容 |

**"非主流程占比"是什么**：防止 AI 只生成 happy path 用例。非主流程包括异常路径、边界值、专项测试（安全/兼容/性能）、资源与 UI 验证、中断恢复等。通过在提示词中写入硬性比例要求，约束模型的输出分布。

### 3.3 提示词工程

提示词是整个系统的核心。分为 System Prompt（角色 + 规则）和 User Content（任务 + 材料）两部分。

**System Prompt 的关键设计**：

| 规则 | 做什么 | 防止什么 |
|------|--------|---------|
| 诚实原则 | 信息不足时输出占位用例（summary 写明缺什么），而非编造 | 防止 AI 凭空想象文档未提及的功能 |
| 字段强约束 | 11 个字段全部必填，类型和格式明确 | 防止输出结构不一致导致解析失败 |
| 方法论内化 | 将等价类/边界值/判定表等方法编入规则 | 防止只走 happy path |
| 展示约束 | 禁止在用例文本中出现方法论术语 | 用例给业务人员看，不能出现"等价类""边界值"等专业术语 |
| 标识符原文约束 | 需求中的 ID/文案/路径必须原样使用，未提及的禁止编造 | 防止 AI 编造不存在的按钮名、配置项 |
| 媒体资源约束 | 仅对需求中实际列出的资源名编写用例 | 防止 AI 杜撰音效/图片名称 |

**User Content 的拼装策略**：

```
用户消息的结构（自上而下拼装）：
├── 时区约定
├── 详细程度描述
├── 数量策略块（最低条数、占比、分布参考）
├── 测试类型列表
├── 关注重点（用户自定义文本）
├── 多文档约定说明
├── 文档材料（按角色标注 + 排序，受字符预算控制）
├── 覆盖要求（标识符、媒体、分支等硬约束）
├── 关键要求清单（增强版 8-9 条）
├── 代码上下文（增强版，可选）
├── 知识库参考（增强版，可选）
├── 方法论正文节选（自动截取前 3400 字）
└── 近期修订倾向（用户编辑历史摘要，自动注入）
```

**字符预算分配**（增强版，总预算约 120,000 字符）：

```
总预算 120,000 字符
  ├── 文档材料：优先保证 ≥ 32,000 字符（最低保留）
  ├── 代码上下文：上限 55,000 字符
  ├── 知识库参考：上限 14,000 字符
  └── 预留开销：约 10,000 字符（配置块、约束文字等）

分配逻辑：文档优先。当代码 + 知识库 + 开销挤压文档到低于 32K 时，
自动压缩代码区块（优先）和知识库区块，确保文档材料不被饿死。
```

### 3.4 方法论驱动的用例设计

提示词中内嵌了 ISTQB 黑盒测试方法论的要求（与仓库中独立的方法论文档对齐），确保生成的用例不仅覆盖功能，还覆盖测试方法论维度：

| 方法论 | 提示词中的要求 | 举例 |
|--------|-------------|------|
| 等价类 | 划分有效/无效输入类，每类至少一条 | 合法金额 / 负数金额 / 零 / 超大值 |
| 边界值 | 有序域覆盖边界及邻域，写出具体数值 | 库存 0/1/最大值/最大值+1 |
| 判定表 | 多条件组合覆盖，不只测单点 | VIP + 满减 + 折扣的组合 |
| 状态与场景 | 首次/非首次、中断恢复、幂等 | 弱网下单 → 杀进程 → 重进 |
| 协议与安全 | 条件型（CD/上限）+ 参数型（非法值） | 过期 token / 负数 ID / SQL 注入 |
| 兼容与环境 | 矩阵抽样 | iOS + Android × 不同分辨率 |

**关键约束**：方法论仅在内部作为检查清单使用。输出的用例 summary/description/remarks 中不允许出现"等价类""边界值"等术语——用户看到的是业务语言，不是测试方法论术语。

### 3.5 增强生成模式（代码 + 知识库）

在基础的"需求文档 → 用例"之上，系统支持注入两种额外上下文：

```
                    基础生成                        增强生成
              ┌──────────────────┐          ┌──────────────────────┐
              │ 需求文档（必须）   │          │ 需求文档（必须）       │
              │       ↓          │          │       ↓                │
              │ AI 生成用例       │          │ + 代码变更摘要（可选） │
              │                  │          │ + 知识库检索（可选）   │
              └──────────────────┘          │       ↓                │
                                            │ AI 生成用例（更全面） │
                                            └──────────────────────┘
```

**代码上下文来源**：

前端「代码变更面板」（CodeChangePanel）支持接入多个版本控制仓库（Git / Plastic SCM），用户选择仓库 + 筛选条件（时间 / 分支 / 变更集），系统自动提取变更代码摘要注入提示词。

增强版 System Prompt 额外增加了代码分析指令（第 8-13 条规则），要求 AI 结合源码理解类结构、函数接口、条件分支、异常处理，针对性地补充边界和异常用例。

**知识库上下文来源**：

系统对接 LightRAG（向量检索），在生成前自动检索与需求相关的历史经验、缺陷模式、业务规则，注入提示词的「知识库参考」区块。AI 参考这些知识设计回归用例，在 remarks 中标注"参考知识库"。

### 3.6 用户修订反馈闭环

```
AI 生成用例 → 用户编辑修改 → 系统自动 diff → 追加到修订日志
                                                    │
                                                    ▼
                                 下次生成时，注入「近期修订倾向」
                                 提示 AI 避免重复同类错误
```

系统自动追踪用户对生成结果的修改（新增/删除/字段修改），提取修改摘要以 JSONL 格式持久化。下次生成时，最近 8 条修改记录自动拼入提示词尾部，引导模型对齐用户偏好。

### 工具分类

系统中的工具分三类：**浏览器端能力**、**服务端 API**、**外部集成**。

| 工具 | 来源 | 做什么 | 为什么需要它 |
|------|------|--------|------------|
| **文档解析库** | 浏览器端（mammoth/pdfjs/xlsx） | 将各种格式文档转为纯文本 | 不依赖服务端，保护用户文档隐私 |
| **Tesseract.js OCR** | 浏览器端 | 图片文字识别（中英双语） | 截图/扫描版文档无法直接提取文字 |
| **提示词拼装模块** | 服务端 prompt.js / prompt-enhanced.js | 将配置 + 文档 + 上下文组装为结构化提示词 | 核心逻辑——决定 AI 的行为和输出质量 |
| **LLM 多通道路由** | 服务端 providers.js | 统一接口适配 9+ 厂商模型 | 一套代码支持 OpenAI/Claude/Gemini/国产模型 |
| **JSON 规范化** | 前后端各一份（normalize.js / normalizeCasesFromJson.ts） | 修复 LLM 的 JSON 格式错误 + 字段校验 | LLM 输出不保证 100% 合法 JSON |
| **VCS CLI 封装** | 服务端（plastic.js / git.js） | 从版本控制系统提取代码变更 | 增强生成需要代码上下文 |
| **LightRAG 客户端** | 服务端（lightrag.js） | 向量检索知识库 | 注入历史经验和缺陷模式 |

## 5. 多模型支持

### 厂商与通道

系统支持 9+ 个 LLM 厂商，全部通过 OpenAI 兼容接口统一接入（Gemini 走 Google SDK）：

| 通道 | 厂商 | 默认模型 | Token 预算模式 |
|------|------|---------|--------------|
| openai | OpenAI | gpt-5.4 | completion_independent |
| anthropic | Anthropic Claude | claude-sonnet-4-6 | completion_independent |
| gemini | Google Gemini | gemini-2.5-flash | — (Google SDK) |
| qwen | 阿里通义 | qwen-turbo | completion_independent |
| ernie | 百度文心 | ernie-4.0-8k | completion_independent |
| doubao | 字节豆包 | (需配置) | completion_independent |
| glm | 智谱 GLM | glm-4 | completion_independent |
| minimax | MiniMax | (需配置) | shared_context_window |
| kimi | Moonshot Kimi | kimi-k2.6 | completion_independent |
| deepseek | DeepSeek | deepseek-reasoner | completion_independent |

**Token 预算模式**：
- `completion_independent`：max_tokens 独立于 prompt 长度，直接设为配置值
- `shared_context_window`：max_tokens + prompt tokens 不能超过上下文窗口，需动态计算

**多模型下拉**：每个通道可在 `.env` 配置多个模型（CSV 列表），前端以下拉框形式展示，后端按白名单校验。

### 流式输出

系统默认使用 SSE（Server-Sent Events）流式输出，前端实时展示 AI 生成过程：

```
事件类型：
├── delta    → 模型输出的文本片段（逐 token）
├── thinking → 推理模型的思考过程（DeepSeek-Reasoner 等）
├── done     → 生成完成，附带规范化后的用例数组
├── error    → 生成出错
└── parse_error → JSON 解析失败（附带原始文本供排查）
```

**中断与恢复**：前端提供停止按钮（AbortController），用户可随时中断生成。中断时已接收的部分文本会尝试解析为用例（补齐未闭合括号），标记为 `partial: true`。

## 6. 踩过的坑与优化经验

### 6.1 模型输出 JSON 格式不合法 → 7 步自动修复

**问题**：LLM 输出的 JSON 经常有格式瑕疵——带 Markdown 围栏、中文引号、尾部逗号、未闭合括号、字符串内裸双引号等，直接 `JSON.parse` 会失败。

**解法**：构建 7 步渐进式修复流程（repairLlmJson）：
1. 提取 JSON 主体（去掉前后说明文字）
2. 中文引号 → 英文引号
3. 尾部多余逗号
4. 不可见控制字符
5. 直接 parse 尝试
6. 转义字符串内裸双引号（最常见错误）
7. 补齐未闭合括号（输出截断时）

**效果**：绝大多数 LLM 输出（包括被截断的不完整输出）都能成功解析。

### 6.2 AI 只走 happy path → 数量策略块 + 非主流程占比约束

**问题**：AI 倾向于只生成"正常操作 → 预期正确"的主流程用例，异常/边界/安全类用例偏少。

**解法**：
1. 在提示词中写入量化的最低条数和非主流程占比要求
2. 按详细程度分三档，每档有不同的数值约束
3. 明确列出"非主流程"包含哪些（异常路径、边界值、专项测试、中断恢复等）

### 6.3 AI 编造不存在的业务细节 → 诚实原则 + 信息不足占位

**问题**：需求文档描述不完整时，AI 会凭空编造功能细节、按钮名称、配置项等，生成看起来合理但实际不存在的用例。

**解法**：
1. System Prompt 最高优先级设为"诚实"——未知不说、绝不捏造
2. 信息不足时必须输出占位用例（summary 写明缺什么、steps 为空、expected 写"信息不足，无法验证"）
3. 标识符原文约束：需求中出现的具体标识必须原样使用，未出现的禁止编造

### 6.4 方法论术语泄露到用例文本 → 展示约束

**问题**：提示词中要求 AI 使用等价类、边界值等方法，但 AI 会把这些术语直接写进用例的 summary 或 description 中（如"等价类：有效输入测试"），让业务人员困惑。

**解法**：在提示词中明确写入展示约束——方法论仅在内部作为检查清单使用，summary/description/remarks 中一律不得出现设计方法术语名，也不得用其作开头标签。

### 6.5 文档截断导致末尾需求被遗漏 → 字符预算管理

**问题**：模型有上下文窗口限制，长文档需要截断。但简单截断会导致文档末尾的需求（如附录优化、退出流程等）被完全丢失。

**解法**：
1. 建立字符预算分配机制（文档 / 代码 / 知识库三部分独立预算）
2. 文档材料有最低保留预算（≥32,000 字符），代码和知识库在文档不足时让步
3. 增强版关键要求第 3 条明确要求"避免遗漏文档末尾或附录要求"
4. 多文件时按角色排序，主需求优先获得预算

### 6.6 用例覆盖不均匀 → 逐步对照要求

**问题**：AI 对需求文档前半部分覆盖详细，后半部分覆盖粗糙甚至遗漏，因为模型在长文本中存在注意力衰减。

**解法**：
1. 提示词中加入"逐段阅读 + 逐步对照"要求
2. 要求 AI 输出前"按步骤清单逐项勾选，确认无段落未被任何用例覆盖"（自检指令）
3. 增强版规则第 11 条：按步骤/功能块拆解，为每一块建立可识别的 module/subModule 分组

### 6.7 不同模型生成质量差异大 → 统一规则框架

**问题**：便宜的模型（如 qwen-turbo）和贵的模型（如 claude-sonnet-4-6）在用例质量上差异显著。

**解法**：
1. 将质量要求硬编码在提示词规则中（而非依赖模型自身判断力）
2. 量化约束（最低条数、占比数值、每步用例数）降低模型理解力的影响
3. Few-shot 思路：方法论节选作为参考标准注入
4. 增强版关键要求清单列出 8-9 条"违反将导致输出不合格"的硬约束

### 6.8 推理模型的思考过程干扰输出 → 思考流分离

**问题**：DeepSeek-Reasoner 等推理模型在输出 JSON 前会有大量"思考过程"文本（以 `reasoning_content` 字段返回），如果混入内容会破坏 JSON 解析。

**解法**：SSE 流式中将 `reasoning_content`（思考过程）和 `content`（实际输出）分离为不同事件类型（`thinking` vs `delta`），前端可选展示思考过程但不混入 JSON 解析。

### 6.9 输出截断（finish_reason=length）→ 短输出自动重试

**问题**：模型输出超过 max_tokens 时会被截断，JSON 不完整。

**解法**：
1. maxTokens 全端点强制下限 8192（部分通道 16384）
2. 流式结束后检查输出长度，若过短且 finish_reason 为 length，自动重试一次（不带 json_object 约束，给模型更多自由度）
3. 截断的 JSON 通过 repairLlmJson 的"补齐未闭合括号"步骤尝试抢救

### 6.10 json_object 模式兼容性 → 自动降级

**问题**：部分模型/通道不支持 OpenAI 的 `response_format: { type: "json_object" }` 参数，传入会返回 400 错误。

**解法**：先尝试 json_object 模式，捕获到 400/不支持相关错误后，自动降级为无 response_format 模式重试（日志记录降级事件）。

## 10. 适用场景与局限性

### 适合

- 有需求文档的项目（详设、PRD、功能说明书）
- 需要快速产出结构化用例的场景（迭代快、需求变更频繁）
- 希望统一用例覆盖标准的团队（方法论驱动，减少个人差异）
- 多种详细程度灵活切换（策划验收 vs QA 全量）
- 有代码仓库和知识库可以增强生成质量的项目

### 不适合 / 有局限

| 场景 | 原因 |
|------|------|
| 无需求文档或需求极度模糊 | 无法提供有效的文档材料给 AI |
| 纯运行时行为验证（"动画是否流畅"） | AI 基于文本生成用例，无法覆盖视觉/体感类测试 |
| 需要精确的性能基线数据 | AI 不知道"响应时间 < 200ms"这个数值是否合理 |
| 高度数据驱动的配置表逻辑 | 配置表内容通常不在需求文档中，AI 看不到 |
| .doc 格式文档 | 浏览器端无法解析旧版 Word .doc 格式，需先转为 .docx |

## 11. 关键设计决策总结

| 决策 | 选了什么 | 为什么 |
|------|---------|--------|
| 文档解析位置 | 浏览器端，不传服务端 | 保护文档隐私，减少服务端负担 |
| 密钥存放 | 仅服务端 .env | 浏览器不接触密钥，安全 |
| 提示词架构 | System + User 分离，前后端各维护一份 | System 控行为规则（稳定），User 装材料（可变） |
| 方法论集成 | 编码进提示词规则 + 自动截取文档节选 | 保证每次生成都遵守方法论，不依赖模型自身知识 |
| 用例格式 | 固定 11 字段 JSON | 前后端统一解析，多视图复用 |
| 输出修复 | 7 步渐进式修复 | LLM 输出不可靠，必须有兜底 |
| 流式输出 | SSE，非 WebSocket | 单向数据流，更简单，HTTP 代理友好 |
| 多模型适配 | OpenAI 兼容接口统一抽象 | 一套代码支持所有厂商，切换成本为零 |
| 双通道设计 | API 生成 + Cursor 辅助 | 零配置也能用（Cursor 通道），有密钥效率更高（API 通道） |
| 字符预算 | 文档优先保证最低预算 | 需求材料是用例的核心依据，不能被代码/知识库挤掉 |
| 用户修订追踪 | 自动 diff + JSONL + 提示词注入 | 无需用户手动反馈，系统自动对齐偏好 |
