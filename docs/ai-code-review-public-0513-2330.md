# AI 代码走查系统 — 设计与实践

> 基于 LLM + 确定性工具链的需求-代码一致性自动验证方案。
> 适用于有明确需求文档的软件项目（已在 Unity C# 游戏项目中落地验证）。

---

## 1. 解决什么问题

| 痛点 | 传统做法 | 本方案 |
|------|---------|--------|
| 需求写完后，要人工逐条核对代码是否实现 | 测试/开发手动 review，耗时且容易遗漏 | AI 自动从需求文档提取检查项，逐条在代码中搜证据并判定 |
| 不同人对同一条需求的判定结论不同 | 依赖个人经验和理解 | 结构化判定规则 + 防护机制，减少主观波动 |
| 代码频繁变更，回归核查成本高 | 每次都要重新人工对照 | 一条指令重跑走查，几分钟出报告 |

**一句话说明**：读需求 → 提契约 → 搜代码 → 给判定 → 出报告。

**核心设计原则**：能用脚本确定性完成的步骤（搜索、扫描、校验），绝不让 LLM 自由发挥。LLM 只负责真正需要语义理解的部分（契约提取、代码阅读判定）。

### Phase 0 环境初始化 — "走查前先准备好工具和数据"

```
走查指令下达
  │
  ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. 代码新鲜度检测：对比文件 mtime+size，确认代码是否有变更   │
│ 2. 依赖图谱加载：优先使用编译器索引，无则正则自建            │
│ 3. 历史反馈加载：读取上次走查的人工标注（准确/误判/遗漏）    │
└─────────────────────────────────────────────────────────────┘
```

### Phase 1 契约提取 — "从需求文档里提炼出要检查什么"

```
需求文档
  │
  ▼
┌──────────────────────────────────────────────────────────┐
│ 1. 读取文档内容                                           │
│ 2. 提取「质量契约」= 一条条可检查的业务规则                │
│    例："玩家死亡后 3 秒内在最近检查点复活"                  │
│ 3. 将复杂规则拆成原子级「子要求 SR」                       │
│    例：SR-1 "死亡后触发复活倒计时"                         │
│        SR-2 "倒计时 3 秒"                                  │
│        SR-3 "复活点为最近检查点"                            │
│ 4. 给每个 SR 标注验证类型 checkType（见下文）              │
└──────────────────────────────────────────────────────────┘
  │
  ▼
📋 契约库 JSON
```

**质量契约 vs 测试用例**：

| | 质量契约 | 测试用例 |
|---|---------|---------|
| 描述 | 「系统应该满足什么」 | 「怎么一步步去验证」 |
| 粒度 | 业务规则（跨场景不变量） | 具体操作步骤 |
| 内容 | 不含文件路径、接口 URL、页面元素选择器 | 包含具体执行细节 |
| 举例 | "引导进度不因退出而重置" | "步骤1：进入引导 → 步骤2：退出 → 步骤3：重进 → 预期：进度保持" |

### Phase 1.7 SR 搜索预执行 🆕 — "脚本先搜一遍，能判的先判"

```
契约库 JSON（所有 SR）
  │
  ▼
┌──────────────────────────────────────────────────────────┐
│ 1. 一次加载所有代码文件到内存索引                          │
│ 2. 对每条 SR 的关键词批量搜索                              │
│ 3. 按 checkType 分流：                                     │
│    ├─ grep_forbidden → 自动判定（搜到=fail / 没搜到=pass） │
│    ├─ runtime_only   → 自动判定（直接 uncertain）          │
│    └─ 其余           → 输出 evidence_candidates           │
│                        （真实文件路径/行号/代码片段）       │
└──────────────────────────────────────────────────────────┘
  │
  ▼
LLM 只需处理脚本无法自动判定的 SR，且引用真实行号
```

> 这一步将部分 SR 从"LLM 全流程判定"降级为"脚本确定性判定"，减少对 LLM 的依赖。

### Phase 2 代码走查 — "拿着契约去代码里找证据、给判定"

对每条 **待 LLM 处理的** 契约，按顺序执行：

```
步骤 1 搜索 ──→ 步骤 1.8 证据预采集 ──→ 步骤 2 阅读 ──→ 步骤 3 判定 ──→ 步骤 4 记录
   │                │                │                │
   ▼                ▼                ▼                ▼
用关键词在代码    打开搜到的文件    根据读到的代码    把判定结果写入
库里全文搜索，    逐个阅读理解，    给出 pass/fail    JSON
找到相关文件      同时做隐式发现    /uncertain 判定

搜索工具：                         判定有防护规则：
├─ Grep（文本搜索）                ├─ Pass 防护（必须有正面证据）
├─ AST 分析（8条自定义规则）       ├─ Fail 推定（搜遍了确实没有）
├─ 引擎资产搜索                    ├─ 豁免自检（防止误判）
└─ 预搜索 evidence_candidates      └─ Few-shot 校准（3个典型示例）
```

### Phase 2.5 Evidence 校验 + 修正循环 🆕

```
走查判定完成
  │
  ▼
┌──────────────────────────────────────────────────────────┐
│ 1. 脚本对每条 evidence 做 3 级磁盘验证                    │
│    ├─ 文件路径是否真实存在                                │
│    ├─ 行号是否在文件范围内                                │
│    └─ 方法名是否出现在该行号附近                          │
│                                                           │
│ 2. 失败项附带修正信息（真实代码内容 + 候选路径）           │
│                                                           │
│ 3. LLM 根据修正信息自我修正 → 脚本重新验证（最多2轮）    │
└──────────────────────────────────────────────────────────┘
```

> 从「事后标记错误」升级为「当场修正错误」——脚本告诉 LLM "你写的第42行实际内容是 XXX"，LLM 据此修正。

### Phase 3 报告生成 — "整理成人能看的报告"

```
走查结果 JSON（机器数据）
  │
  ▼
┌───────────────────────────────────────────┐
│ 总览统计（多少条 pass / fail / uncertain）│
│ 逐条展示判定详情 + 证据 + 缺口            │
│ 附带发现（走查中顺带发现的问题）           │
└───────────────────────────────────────────┘
  │
  ▼
脚本自动校验报告完整性（是否有遗漏区段）     ← 🆕
  │
  ▼
📊 走查报告.md（给人看的）
```

## 3. 核心设计

### 3.1 子要求拆解 (Sub-Requirement, SR)

一条业务规则可能包含多个可独立验证的断言。例如：

> 规则："选中带激活效果的组件时，影响范围内格位显示高亮，被影响组件增加特效；取消选中后高亮和特效消失"

拆为 3 个 SR：
- SR-1：选中时格位显示高亮
- SR-2：被影响组件增加特效
- SR-3：取消选中后高亮和特效消失

**为什么要拆**：如果整体判定，AI 可能因为 SR-1 通过了就整条判 pass，漏掉 SR-2 其实没实现。拆开后每个 SR 独立判定，任一 fail → 整条 fail。

### 3.2 checkType 路由（共 5 种）

每个 SR 根据其性质分配一种 checkType，决定"用什么方式去验证"：

```
                        子要求 SR
                           │
                     checkType 是什么？
                           │
         ┌────────┬────────┼────────┬────────┐
         ▼        ▼        ▼        ▼        ▼

   grep_existence  grep_forbidden  ast_pattern  llm_semantic  runtime_only
   "功能存不存在"   "禁止的东西      "代码结构     "需要读懂     "只能运行
                    有没有出现"       匹配"        代码语义"     时才能看出"

   搜关键词        搜关键词          AST工具      AI 阅读       跳过搜索
   搜到→可能pass   搜到→fail        结构匹配     代码后判定     直接标
   没搜到→fail     没搜到→pass                                 uncertain
```

| # | checkType | 适用场景 | 判定方式 | 举例 |
|---|-----------|---------|---------|------|
| 1 | `grep_existence` | 某功能/方法是否存在 | 脚本预搜索 + LLM 确认 | "复活功能" → 搜 `Respawn` |
| 2 | `grep_forbidden` | 需求明确禁止的东西 | **脚本自动判定**：搜到 = fail | "不做弹簧平滑" → 搜 `SmoothDamp` |
| 3 | `ast_pattern` | 代码结构模式匹配 | AST 工具自定义规则匹配 | "事件 += 有没有对应 -="、"空方法体" |
| 4 | `llm_semantic` | 需要理解代码含义 | AI 判定（受防护规则约束） | "死亡后倒计时逻辑是否正确" |
| 5 | `runtime_only` | 纯运行时行为 | **脚本自动判定**：直接标 uncertain | "动画播放是否流畅" |

**设计理念**：能用程序确定性判定的（1/2/3/5），绝不让 AI 来判。AI 只负责真正需要语义理解的部分（4）。这是控制成本和稳定性的关键。

### 3.3 判定防护规则体系

**为什么需要防护规则**：纯靠 AI 判定会产生两个典型问题：
- **虚高通过**：搜到了文件名就判 pass，实际功能并未完整实现
- **判定偏软**：明明代码里完全没有某功能，AI 不敢判 fail，总是判 uncertain

防护规则就是对 AI 判定行为的硬约束：

| 层级 | 规则名 | 通俗解释 | 防止什么 |
|------|--------|---------|---------|
| 1 | Pass 防护铁律 | 想判通过？先证明每个子要求都有实打实的代码证据 | 防止虚高通过 |
| 2 | Fail 推定规则 | 关键词搜遍全库确实 0 结果 → 功能确实没做 → 判 fail | 让真正缺失的功能被准确标记 |
| 2.1 | 强制豁免自检 | 判 fail 前先排除 3 种假阴性（见下方） | 防止「搜不到关键词就判 fail」的误杀 |
| 2.2 | 空实现条款 | 方法存在但函数体为空 → 没做就是没做 | 防止空壳方法被当作已实现 |
| 3 | 否决铁律 | 代码里发现了和需求矛盾的证据 → 绝不能判通过 | 防止有矛盾证据还硬判 pass |

**强制豁免自检的 3 种检查**：

> 背景：搜关键词搜不到 ≠ 功能没做。开发可能换了名字、用了通用机制、或放在配置里。

| # | 检查场景 | 怎么检查 | 举例 |
|---|---------|---------|------|
| A | **通用机制实现** | 功能是否通过通用系统间接完成？ | 需求写「拖拽失败后回退」，没有专属方法，但通用 OnDrop 里有位置重置逻辑 |
| B | **回调/事件模式** | 功能是否通过回调参数、委托、事件派发实现？ | 需求写「点击任意位置关闭」，没有 anyClick 方法，但通过回调委托实现 |
| C | **配置驱动** | 功能是否通过引擎配置/资产文件实现？ | 需求写「按钮高亮」，代码里没设置颜色，但 UI 资产里已配置高亮色 |

```
搜索关键词全库 0 命中 → 准备判 fail
  │
  ├─ A 通用机制检查 → 找到了？→ 豁免为 uncertain
  ├─ B 回调模式检查 → 找到了？→ 豁免为 uncertain
  ├─ C 配置驱动检查 → 找到了？→ 豁免为 uncertain
  │
  └─ 三项全部没找到 → 确认判 fail
       │
       └─ 但如果找到了对应方法，方法体是空的 → 空实现条款 → 仍然 fail
```

### 3.4 附带发现与违规性分级

走查过程中，AI 阅读代码时可能顺带发现与当前契约无直接关系的问题。按严重程度分 4 级：

| 违规性 | 含义 | 后续动作 |
|--------|------|---------|
| **违规** | 与需求文档某条明确约束矛盾 | 升级为新契约或补充为当前契约的 SR → fail |
| **潜在违规** | 看起来不对但无直接矛盾条款 | 需与策划/开发确认 |
| **建议改进** | 代码质量问题，不违反需求 | 值得修复但不阻塞 |
| **待确认** | 需运行时验证 | 下次测试时关注 |

### 3.5 Evidence 程序化验证 + 修正循环

**为什么需要这个**：AI 有时会"幻觉"——编造不存在的文件路径或行号作为证据。如果不校验，报告里的证据可能是假的。

**做法**（两代演进）：

| | v1 做法（事后标记） | v2 做法（当场修正）🆕 |
|---|---|---|
| 验证 | 脚本做 3 级磁盘验证 | 同左 |
| 失败处理 | 标记 `verified: false`，人看到后手动确认 | 附带真实代码内容 → LLM 自我修正 → 重新验证 |
| 效果 | 知道哪些证据有问题，但不修 | 大部分错误可以当场修复 |

```
验证失败的 evidence
  │
  ▼
脚本提供修正信息：
├─ actual_content: "这一行的真实内容是 xxx"
├─ suggested_paths: "文件可能在 A/B/C 路径"
├─ total_lines_in_file: "文件共 200 行，你写的 350 行超出范围"
  │
  ▼
LLM 根据修正信息更新 evidence → 脚本重新验证（最多2轮）
```

> 此环节由代码确定性控制，不依赖 AI 自己说"我确认过了"。

## 4. 工具链架构

### 工具与数据的关系

```
                    ┌──────────────────────────────────────────────────────┐
                    │                   走查执行过程                       │
                    │                                                      │
 契约库 ──────────→│   ①预搜索        ②搜索+判定       ③验证+修正       │
                    │   [脚本自动]      [LLM]             [脚本+LLM]       │
 依赖图谱 ────────→│                                                      │
                    │   关键词批量搜 ─→ AI 阅读+判定 ──→ 证据磁盘验证     │
 映射缓存 ────────→│        │              │               │              │
                    │   AST 结构扫描   防护规则约束     修正信息→LLM修正  │
                    │        │              │               │              │
                    │        ▼              ▼               ▼              │
                    │   auto_judged    走查结果JSON ←── 验证通过的证据     │
                    │   (确定性判定)        │                               │
                    │                      ├──→ 映射缓存更新               │
                    │                      │                               │
                    └──────────────────────│───────────────────────────────┘
                                           │
                                           ▼
                                     走查报告.md → 报告校验脚本
```

### 工具分类

系统中的工具分三类：**IDE 内置能力**、**自主开发的辅助脚本**、**外部编译器索引**。

| 工具 | 来源 | 做什么 | 为什么需要它 |
|------|------|--------|------------|
| **Grep** | IDE 内置 | 代码库全文搜索 | 走查基础 |
| **AST 扫描脚本** | 自主开发 | 分析代码结构（8 条自定义规则）| Grep 只能搜文本不懂结构 |
| **SR 预搜索脚本** 🆕 | 自主开发 | 批量关键词搜索 + 确定性 SR 自动判定 | LLM 搜索时会编造行号 |
| **证据验证脚本** | 自主开发 | 检查证据真伪 + 提供修正信息 | AI 幻觉问题 |
| **依赖图谱** 🆕 | 外部编译器 / 自建 | 类间依赖关系 + 文件结构索引 | 纯 Grep 缺乏代码结构信息 |
| **映射缓存脚本** | 自主开发 | "模块→代码文件"对应关系缓存 | 加速重复走查 |
| **报告校验脚本** 🆕 | 自主开发 | 检查报告必要区段是否齐全 | LLM 有时遗漏报告区段 |
| **仓库配置脚本** | 自主开发 | 统一管理多仓库路径 | 路径格式不一致导致出错 |

> **设计原则**：AI 擅长理解语义但不可靠，脚本不懂语义但确定性高。让 AI 做它擅长的（阅读理解），用脚本约束它不擅长的（精确搜索、证据校验、缓存管理）。

### AST 自定义规则库（8 条）

| 规则 | 检测内容 | 匹配方式 | 用途 |
|------|---------|---------|------|
| 空方法体 | 方法体为空 | AST 节点类型 + 正则 | 直接支撑空实现条款判定 |
| 事件订阅配对 | `+=` / `-=` 赋值 | AST 节点类型 + 正则 | 找出只订阅未取消的事件（内存泄漏风险） |
| 协程无 yield | IEnumerator 无 yield | AST 节点类型 + 子节点检查 | 未完成的协程实现 |
| GetComponent 调用 | GetComponent 调用点 | AST 模式匹配 | 标记检测点，供后续分析 null 安全 |
| 单例模式 🆕 | 静态 Instance 属性 | AST 节点类型 + 正则 | 设计模式标签 |
| ScriptableObject 🆕 | SO 配置类 | AST 节点类型 + 正则 | 设计模式标签 |
| 对象池使用 🆕 | ObjectPool 调用 | AST 节点类型 + 正则 | 设计模式标签 |

> **踩坑经验**：初版规则使用 pattern 语法（直接写代码片段匹配），实测发现 AST 工具的 C# 解析器对 Allman 大括号风格（`{` 独占一行）和复合赋值运算符（`+=/-=`）支持不佳。修正方案：改为基于 AST 节点类型 + 正则的结构化匹配，修正后全部规则在两个不同项目上验证通过。

### 依赖图谱双源架构 🆕

| 项目条件 | 图谱来源 | 精度 | 速度 |
|---------|---------|------|------|
| 有编译器索引文件 | 编译器（如 Roslyn）生成的结构化索引 | 高（含继承/接口/泛型） | ~150ms |
| 无编译器索引文件 | 脚本正则扫描 .cs 文件自建 | 低（仅正则匹配） | ~2s |

> 优先使用编译器索引，无则降级自建。两套数据通过统一接口访问，上层不感知来源。

### 数据文件说明

| 文件 | 一句话解释 | 写入方 | 读取方 | 保留策略 |
|------|-----------|--------|--------|---------|
| **契约库 JSON** | 从需求文档提取的"要检查的规则"清单 | Phase 1 | Phase 1.7 + Phase 2 | 永久保留，可追加 |
| **走查结果 JSON** | 每次走查的详细机器数据 | Phase 2 | Phase 2.5、Phase 3 | 永久保留，按日期追加 |

## 5. 仓库支持

系统支持同时接入多个代码仓库。走查时根据契约内容自动选择相关仓库进行搜索。

支持的仓库类型：Git、Plastic SCM 等常见版本管理工具。通过统一的仓库配置脚本管理路径和文件格式，确保跨仓库的 evidence 路径一致性。

当前已在 2 个不同项目（5 个仓库）上验证通过。

## 6. 踩过的坑与优化经验

### 6.1 AI 判定不稳定 → 子要求拆解 + 确定性分流

**问题**：用不同 LLM 模型对同一需求走查，结果差异很大。

**根因**：让 AI 对一整条复合规则做端到端判定，容易遗漏子项。

**解法**：规则拆解为原子级 SR → 程序确定性判的不让 AI 判 → AI 只处理语义理解部分 → 加防护规则硬约束。

**效果**：不同模型的判定一致性显著提升，可以用较便宜的模型达到接近贵模型的质量。

### 6.2 虚假 Pass → Pass 防护铁律

**问题**：AI 搜到了相关文件就判 pass，实际只搜到了类名而非具体功能。

**解法**：每个 SR 必须有 ≥1 条正面 evidence，否则最高只能判 uncertain。

### 6.3 判定偏软 → Fail 推定规则

**问题**：AI 很少主动判 fail，全库搜索 0 命中也说"可能在其他地方"。

**解法**：关键词 ≥3 种变体全库 0 命中 + AST 无调用链 → 判 fail，不允许 uncertain。

### 6.4 假 Fail → 豁免自检 / 6.5 豁免过度 → 空实现条款

**问题**：Fail 推定过严会误杀（用了不同名字/模式的功能），豁免过宽又会放过空壳方法。

**解法**：两者互制——豁免自检（防误杀）+ 空实现条款（防过度豁免），达到平衡。

### 6.6 否定式约束漏检 → grep_forbidden

**问题**："不做 X"类否定式约束，AI 倾向给 uncertain。

**解法**：独立 checkType，搜到 = fail，搜不到 = pass。不进入语义分析。

### 6.7 AI 证据幻觉 → Evidence 程序化验证 + 修正循环 🆕

**问题**：AI 给出的 evidence 中文件路径/行号有时是编造的。

**解法**（v2 升级）：走查后用脚本做 3 级磁盘验证。失败项附带真实代码内容和候选路径，LLM 据此自我修正后重新验证（最多2轮）。从"事后标记"升级为"当场修正"。

### 6.8 附带发现被忽视 → 违规性分级

**问题**：严重 bug 和轻微建议混在一起，无法区分轻重。

**解法**：4 级违规性标注（违规 / 潜在违规 / 建议改进 / 待确认）。

### 6.9 AST 确定性判定不足 → ast-grep 自定义规则库

**问题**：`ast_pattern` 类型一直降级为 grep。

**解法**：创建 8 条自定义规则。全部改为 AST 节点类型 + 正则匹配（绕开 pattern 解析限制），在两个项目上验证通过。

### 6.10 LLM 判定不一致 → Few-shot 校准

**问题**：不同模型对同样证据做出不同判定。

**解法**：3 个典型示例（pass / fail / uncertain 各一个），LLM 判定时对照校准。

### 6.11 AI 遗忘搜索结果 → 证据预采集

**问题**：LLM 在判定时遗忘或编造搜索阶段的结果。

**解法**：步骤 1.8「证据候选汇总」，判定时必须从此列表中引用。

### 6.12 LLM 不执行指令 → 脚本硬编码 🆕

**问题**：多个优化步骤写在规则文件中让 LLM 执行，但 LLM 遵从度不稳定，经常跳步。

**解法**：创建 Python 统一入口脚本，将所有确定性步骤硬编码。LLM 只需调用一条命令，脚本内部自动串联所有子步骤。

### 6.13 LLM 搜索编造行号 → SR 搜索预执行 🆕

**问题**：LLM 自行调用搜索工具时，有时记错或编造搜索结果的文件路径/行号。

**解法**：在 LLM 判定前，用 Python 脚本对所有 SR 关键词执行真实搜索，输出结构化结果（真实 file/line/snippet）。LLM 从中选取而非自行搜索。

### 6.14 自建依赖图谱精度低 → 双源架构 🆕

**问题**：正则自建的图谱精度低，大部分场景下是 0 边图谱。

**解法**：优先使用编译器（Roslyn）生成的索引文件，精度更高且速度更快。无编译器索引时降级为自建。

## 8. 走查报告解读

### 报告结构

```
📊 走查报告
├── 总览表（契约数量、通过/违规/存疑统计、工具状态）
├── 走查详情（逐条契约）
│   ├── 规则 + 边界提示
│   ├── 子要求判定表（每个 SR 的独立结论）
│   ├── 汇总判定
│   ├── 证据列表（文件、行号、方法名、说明）
│   ├── 缺口说明（证据不足的部分）
│   └── 附带发现（含违规性分级）
└── 未走查契约（非 code_review 类型）
```

### 判定含义

| 判定 | 含义 | 行动 |
|------|------|------|
| ✅ pass | 找到充分证据支撑规则成立 | 无需行动 |
| ❌ fail | 确认功能缺失或与规则矛盾 | 需开发修复 |
| ❓ uncertain | 证据不足以判定 | 需人工确认或运行时验证 |

### 置信度

| 范围 | 含义 |
|------|------|
| 75-95% | 关键路径找到，逻辑完全吻合或明确矛盾 |
| 40-65% | 找到部分代码，关键路径不完整 |
| 5-35% | 无法定位相关目录或文件，材料严重不足 |

## 10. 适用场景与局限性

### 适合

- 有明确需求文档的项目（详设、PRD、功能说明书）
- 代码可被文本搜索的项目（非混淆/非二进制）
- 需要高频回归核查的场景（版本迭代快、代码频繁变更）
- 有多个代码仓库需要交叉验证的项目

### 不适合 / 有局限

| 场景 | 原因 |
|------|------|
| 纯运行时行为验证（"动画是否流畅"） | 代码走查无法覆盖，标为 uncertain |
| 无需求文档或需求极度模糊 | 无法提取有效契约 |
| 高度动态的配置表/数据驱动逻辑 | 代码中看不到最终行为，需结合数据分析 |
| 第三方 SDK / 加密代码 | 无法搜索和阅读 |

## 11. 关键设计决策总结

| 决策 | 选了什么 | 为什么 |
|------|---------|--------|
| 判定单元 | 原子级子要求（SR），非整条规则 | 防止复合规则下的子项遗漏 |
| 搜索策略 | 脚本预搜索 + AI 补充 🆕 | 确定性 > AI 理解力，且避免 LLM 编造行号 |
| 判定约束 | 硬编码防护规则，非纯 AI | AI 有判定偏好（偏 pass），需要规则纠偏 |
| 证据校验 | 脚本磁盘验证 + 修正循环 🆕 | AI 幻觉不可忽视，且需当场修正 |
| 缓存设计 | 按模块缓存映射，增量积累 | 重复走查场景多，加速效果显著 |
| 否定约束 | 独立 checkType（grep_forbidden），脚本自动判定 🆕 | 否定约束是二值判定，不应进入语义分析 |
| AST 规则匹配 | AST节点类型+正则优先，pattern 备选 | pattern 语法对特定语言风格兼容性不足 |
| 依赖图谱 | 编译器索引优先，正则自建降级 🆕 | 编译器精度高且速度快 |
| 流程控制 | 脚本硬编码，非规则文件指令 🆕 | LLM 对长指令遵从度不稳定 |
